# SBOM (CycloneDX) — o que é e o que não é

`scripts/sbom_from_verification_metadata.py` gera um SBOM no formato
[CycloneDX 1.5](https://cyclonedx.org/docs/1.5/json/) (JSON) a partir de
`gradle/verification-metadata.xml`. Só Python 3 padrão, sem dependências.

## Como gerar

```sh
python3 scripts/sbom_from_verification_metadata.py > sbom.cdx.json
python3 -c 'import json; json.load(open("sbom.cdx.json"))'   # sanidade
```

O CI (`.github/workflows/ci.yml`) e o release (`.github/workflows/release.yml`)
geram e anexam esse arquivo automaticamente.

## O que cobre

- Cada `<component group name version>` do `verification-metadata.xml` vira um
  componente `library` com `purl` `pkg:maven/<group>/<name>@<version>`.
- Quando o componente tem exatamente um artefato binário (`.aar` ou `.jar`),
  o SHA-256 dele vira `hashes` do componente. Medido em 16/09/2026: 396
  componentes, 286 com `hashes`; dos 110 sem, 107 só têm `.pom`/`.module`
  (BOMs, POMs-pai, metadados) e 3 têm mais de um binário (`aapt2` linux/osx,
  `guava` android/jre, `kotlin-stdlib` normal/all) — todos continuam com cada
  hash em `properties`.
- Todo artefato (`.aar`, `.jar`, `.pom`, `.module`) fica registrado em
  `properties`, no formato
  `gradle:verification-metadata:artifact:<arquivo>` = `SHA-256:<hex>`.
- `metadata.component` é o app, com `versionName`, `versionCode` e
  `applicationId` lidos de `app/build.gradle` (só leitura; nada é alterado).

## O que NÃO cobre — leia antes de citar este SBOM

1. **Não é análise do APK/AAB.** Ele não diz o que foi de fato embutido no
   binário: o R8 remove código e `dependenciesInfo` está desligado no build.
2. **Não distingue escopo.** O arquivo de verificação mistura runtime,
   compilação, testes, lint e plugins de build (AGP, Kotlin) — tudo aparece
   igual, como `library`.
3. **Sem grafo de dependências** (o SBOM não tem `dependencies`): o metadata
   não registra quem depende de quem.
4. **Os hashes são os que o Gradle gravou ao resolver** (`origin="Generated by
   Gradle"`), com `verify-signatures=false`. Eles garantem que o build usa os
   mesmos bytes de então, não que os bytes vieram do autor original.
5. **Só cobre o que está no arquivo.** Dependência nova sem entrada no metadata
   quebra o build antes de faltar no SBOM (verificação estrita), mas o arquivo
   pode conter entradas órfãs de dependências já removidas.
6. **Ferramentas fora do Gradle** (SDK Android, NDK, JDK, `gradle-wrapper.jar`)
   não aparecem.

## Por que não o plugin CycloneDX do Gradle

Adicionar `org.cyclonedx.bom` (ou `gradle/actions/dependency-submission`, que
injeta um init-script) exige registrar os checksums do plugin e de tudo o que
ele puxa em `gradle/verification-metadata.xml` — e isso só se faz com o SDK
Android instalado, resolvendo tudo de verdade. Quando esse passo for feito, o
plugin pode substituir este script e trazer escopo e grafo de dependências.

## Reprodutibilidade

`serialNumber` é um UUID novo a cada execução (identificador do documento,
exigido pelo formato). `timestamp` respeita `SOURCE_DATE_EPOCH`. Os componentes
saem ordenados por (group, name, version) e os artefatos por nome.
